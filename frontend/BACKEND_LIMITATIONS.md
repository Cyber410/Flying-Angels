# Running backend limitations — Sprint 2

This is the running list of limitations encountered while building Sprint 2.
All remain open unless explicitly marked resolved. No backend fixes have been
authorized. Build, lint, and automated tests are deferred at the user's request.
Update this file whenever a limitation, workaround, or resolution changes.

| ID | Limitation and evidence | Current frontend behavior / impact | Backend support needed later |
| --- | --- | --- | --- |
| BL-01 | **Unscored assignment crashes.** `EventService.assignParticipant` passes a null result; the `EventResult` constructor calls `result.trim()`. | The broken participants POST is bypassed. Unscored assignments live in this browser, clearly labeled. The first actual result creates the shared record through the results POST. Teammates cannot see pending assignments. | Allow a null result when creating an assignment; retain null score until a result exists. |
| BL-02 | **One result per athlete/event.** `EventResult` has a unique `(event_id, athlete_id)` constraint; `EventService.addResult` rejects duplicates. | Multiple editable attempts are kept in this browser. Only the best value is stored through the existing API. Other devices see that shared best value, not the full attempt history. Clearing browser data loses the extra attempts. | Separate participants from attempts, with stable attempt IDs and CRUD endpoints. |
| BL-03 | **No event/performance notes API.** Event/EventResult have no note field; controllers expose no notes endpoint. The athlete's general note is a separate field. | Event/performance notes remain browser-only. The profile Notes tab separates the shared general athlete note from browser-only performance notes; Meet Details uses the same performance-note storage. | Add notes scoped to events and/or athlete participation, with persistence and endpoints. |
| BL-04 | **No meet status.** `Meet`, `MeetRequest`, and `MeetResponse` expose no status field. | Status columns/filters from the wireframe are deferred; status is not guessed from the date. | Define meet statuses and expose them in create/update/list responses. |
| BL-05 | **One meet date, no date range.** Meet DTOs have `meetDate` only. | Meets show a single Date column. From/To filters search that date; they are not separate start/end dates for a meet. | Add start/end dates and validation if multi-day meets are required. |
| BL-06 | **No explicit result unit metadata.** Event/category DTOs provide names, eventType and rankingOrder, but no unit. | The frontend infers time vs distance and suggests a default. Users choose seconds, decimal minutes, minutes + seconds, hours + minutes + seconds, or metres/centimetres as appropriate. Changing units converts the current value; editing restores the recorded unit. The display string retains the choice, while score is normalized to seconds/metres. Custom event dimensions still rely on name/type/ranking heuristics. | Store measurement type and entered unit/value independently of ranking order and display text; expose supported units for each category. |
| BL-07 | **No combined results/history endpoint.** EventController offers the event index, individual profiles and per-event leaderboards only. | Results Overview and Athlete Profile history share a loader that assembles event profiles in batches of at most six. Individual failures are disclosed. Loading many events costs multiple requests. | Add combined result/history queries with event/meet/athlete context. |
| BL-08 | **Result DTOs omit age/gender information.** `EventResultResponse` has athlete names/ID but no DOB, age group, or gender. | Results Overview joins the athlete directory. Missing demographic data remains “Not provided”; failed demographic loading is disclosed. Age groups are derived from DOB at the event date, not stored competition divisions. | Include or join athlete metadata and clarify whether historical competition age groups must be stored. |
| BL-09 | **No server pagination/filtering for the meet/event indexes or cross-meet results.** Existing meet/event list methods return full lists. | Search/filtering/pagination happen locally after loading the available data. Athlete directory search exists separately. | Add pagination and filter parameters for these queries as data grows. |
| BL-10 | **No copy-events or batch mutation endpoint.** Event creation/participant mutation endpoints handle individual records. | Copy Events creates only event definitions, one at a time. Partial successes are preserved and failed selections stay available for retry. Copying does not include athletes/results. | Add batch/copy operations with defined transaction and duplicate behavior. |
| BL-11 | **Results require a numeric score.** Result request DTOs require nonblank result plus nonnegative score; no performance-status field exists. | The editor accepts numeric times/distances. DNS, DNF, DQ and similar outcomes cannot be stored without inventing a score, so they are not fabricated. | Add explicit performance statuses and permit absent numeric scores where appropriate. |
| BL-12 | **Athlete profile results lack event/meet identity.** `AthleteProfileResponse.events` uses `EventResultResponse`, which has category info but no event ID, meet ID/name, or event date. | The Meets & Results profile tab joins event/meet indexes and event profiles, then adds this browser's assignments/attempts. Failed events are disclosed. Unmatched profile records remain under Other recorded results; confirmed result IDs are not displayed twice. History stays loaded when switching tabs. | Return meet/event identity and dates with an athlete's performances or add an athlete-specific history endpoint. |
| BL-13 | **Imported/unlinked performances cannot be attributed to a meet.** `recordImportedResults` creates EventResult records with a null event; the event index/profiles do not expose them. | Results Overview is scoped to results recorded in meets. Unlinked historical/imported performances are not assigned invented meets. Import remains another teammate's scope. | Expose unlinked results separately and define how they can be associated with meets/events. |
| BL-14 | **Unexpected failures return a generic message.** `ApiExceptionHandler.unexpected` responds with “An unexpected error occurred.” | The UI displays the response. Diagnosis may require code/log inspection, as with BL-01. | Improve server-side diagnostics and structured handling for known failures; keep internal details out of public responses. |
| BL-15 | **Imported category creation always defaults to ascending ranking.** `EventService.recordImportedResults` passes `RankingOrder.ASC` when resolving every imported category, including field-event names. | Event selection inherits a category's configured ranking; known field names get metre units, but unit inference does not correct ranking. Existing imported categories and their events need review before relying on field-event best/leaderboard order. This is a code finding; current database configurations have not been audited. | Define discipline-aware category ranking defaults and a way to review/correct existing configuration. |
| BL-16 | **Fixed score precision/range and unstructured display text.** `EventResult.score` is DECIMAL(12,4); `result` is a string limited to 50 characters. | Converted scores are normalized to seconds/metres, rounded to four decimals, and must be below 100,000,000. The entered unit remains in the display string. Extremely close attempts can tie after score rounding; unit conversion is a client responsibility. | Validate numeric bounds/precision explicitly in the API and define structured measurement/unit fields if higher precision or lossless entry values are required. |
| BL-17 | **Athlete profile selects central OR legacy results.** `AthleteProfileResponse.from` returns legacy athlete events only when `centralResults` is empty; otherwise it returns central results alone. | The original profile summary is preserved as returned by the API. Legacy-only performances can disappear from that response once central results exist, unless they were migrated. The frontend cannot recover omitted records or assign them invented meets. Current data has not been audited for omissions. | Migrate legacy results or merge both sources with stable identities and a defined deduplication rule. |

## Browser storage used by the workarounds

- Pending assignments: `flying-angels:pending-event-assignments:{eventId}`
- Attempts: `flying-angels:event-attempts:{eventId}:{athleteId}` (plus temporary `:staged`)
- Notes: `flying-angels:event-note:live:{eventId}:{athleteId-or-event}`

These stores are specific to the browser and frontend origin. They are not shared
database records. Sample data uses negative IDs and a separate notes namespace.
